执行原则
1. 新的约 10 篇用作开发和校准，可以包含原五篇及五篇新论文；不把它们当作未触碰的最终 test。
2. 近期约 100 篇正式 baseline benchmark 用于 model selection，登记为 selection benchmark，不称为未用于任何开发决策的 final test；它与十篇开发论文及训练论文分开，重复版本按论文身份去重。后续另保留独立 final test；final test 不参与 prompt、rubric、模型、checkpoint 或训练选择。
3. 先在十篇开发数据决定样本数、prompt、评估规则和运行设置，再冻结 baseline benchmark。正式比较期间不改变 prompt/rubric 或补有利样本；需要新设计时登记为新的开发实验。final test 只在学生模型和训练方案冻结后用于最终报告。
4. 模型输入为相同的清理后全文，输出先沿用英文单段摘要。建议新一轮统一目标为 150 词；这是计划默认值，不是老师指定值。在开发 pilot 中验证后冻结，长度独立于 reference。字数合规仅作诊断，不作质量替代。
5. 每个模型用官方接口/chat template；保持等价任务要求，记录 tokenizer、context、量化、后端及 prefill 差异。历史结果与新协议结果分开存放，不平均混合。
6. 同一组候选摘要分别对 GPT reference 和作者 abstract 评分；切换 reference 不重生成候选。
7. 先沿用已有五个质量维度，建议改成 1–10、允许小数并写明评分锚点；不把五维总分当事实正确性的证明。老师允许的 1–100 是替代尺度，没有明确要求必须采用。
8. 生成、reference、quality judgment 和 factual judgment 分开保存，支持按阶段恢复，失败保留原因，不填零或当作无错误。
9. 大文件、模型、环境、缓存及运行输出留在 /data；执行前核对实际服务器目录和共享权限。每轮单独输出目录，历史输出保持可追溯。

任务 4 GPT 评分校准与事实反转测试（第 4–5 个工作日，可与资源分析交错）

任务 5 检查 batching 和决定正式规模（第 5–6 个工作日）
行动：
[ ] 在固定的开发子集比较逐篇处理与小批量/并发请求，先比较实际同时处理数 1 和 2；若稳定且有收益，再决定是否继续增加。
[ ] 同一时刻优先只加载一个生成模型；记录与原始逐篇设置的差异，不把预处理/HTTP 并发误称为 GPU batch inference。
[ ] 保持每篇独立摘要，检查实际吞吐、延迟、OOM、摘要和 prompt 的正确配对。batching 无收益或不支持时，保留稳定逐篇方案。
[ ] 用 pilot 的总生成时间、judge 时间、失败重试比例和可用资源估算正式 100 篇的成本。
[ ] 初步建议正式规模为 100 篇；若预算、时间及覆盖需求允许，可在看正式结果前改为 500 篇。500 不是会议的固定配额。
交付：batch 可行性与吞吐对比、正式样本数及资源依据。
验收：用实测数据解释选择；不把老师举的一次 50 篇、1–2 小时完成等数字写成硬件能力或保证。

规模说明：100 篇 × 4 模型 = 400 个候选；每候选分别评分两类 reference，共 800 个 reference 条件比较。若 quality 与 factuality 分开各一条请求，则约 800 次 judge 请求，未包括 reference 生成、重试和额外复核；实际调用方式在任务 1 确认。

后续阶段 SFT 的进入条件与计划
进入条件：
[ ] baseline 和 judge 流程可复现，reference 来源及模型身份可追溯。
[ ] student 候选及其实际全文长度预算明确，训练、验证、final test 划分已经固定；final test 与 pilot/selection benchmark 分开。
[ ] teacher model、生成 prompt、过滤和人工抽查规则、生成费用/额度落实。
[ ] 能用与最终目标一致的输入长度在 H100 MIG 24 GB 做训练可行性试验；能推理不等于能训练。

执行顺序：
1. 用独立于正式 test 的少量论文建立 teacher 数据 pilot，检查配对、来源与事实支持，再决定正式规模。
2. 先做数据格式和少量更新步骤的训练试验，记录真实显存、序列长度、有效 batch、运行时间及保存/恢复情况。
3. 若全文长度下超出显存，明确评估内存优化、较小 student 或改变输入策略的代价；不能静默截断后仍称为同一全文任务。
4. 使用 development/validation 选择训练设置与 checkpoint；不根据 test 分数调参。
5. base 与 fine-tuned 在同一实际推理后端、相同输入、prompt、references、生成/量化设置及 judge 下做最终配对评估。旧 Ollama base 分数不能直接和新 HF fine-tuned 分数当作只改变训练的对照。
6. 冻结 student 和训练方案后使用独立 final test 做一次最终比较；近期约 100 篇 selection benchmark 的分数不是 final test 分数。final test 的论文数按独立样本覆盖、可得数据与最终评估预算，在训练前固定。
7. 报告质量改善、事实错误、训练开销和推理效率；网页接入与新增合作者协调，学生优先完成研究结果。
